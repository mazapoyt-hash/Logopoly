# CoinScope

Сканер криптовалют, который выдаёт сигналы **Лонг / Шорт** с уровнями входа,
стопа и тейка — и **честно считает, чем каждый сигнал закончился**.

## Про «точность» — сразу и прямо

Никакая система не предсказывает рынок с гарантированной точностью. Если бы
предсказывала, её бы не продавали, а тихо использовали. Поэтому здесь слово
«проверенный» означает ровно одно:

- каждый сигнал проходит **бэктест по истории** без подглядывания вперёд;
- каждый выданный сигнал **отслеживается вживую** до стопа или тейка;
- на сайте показывается **фактический результат**, включая убытки, а не
  заявленный винрейт.

Статистика считается одними и теми же правилами для истории и для живых
сигналов, поэтому цифры сопоставимы. Винрейт не выносится в заголовок, пока
сделок меньше 20 — на малой выборке это шум, а не доказательство.

### Текущий результат: сигнала нет

На реальных данных Binance — 8 монет, 1h, 8000 свечей на монету (11 месяцев),
2257 сделок — стратегия убыточна: винрейт 36.7%, средний −0.12R, profit factor
0.83, суммарно −271R. Но важнее не это, а **почему**:

| Проверка | Результат |
|---|---|
| Score ранжирует сделки | Нет — ни одна из 5 групп не выделяется |
| Входы бьют случайные (с издержками) | Нет — 20-й процентиль |
| Входы бьют случайные (без издержек) | Нет — **11-й процентиль** |
| Находки выше измеренного шума | Нет — 12 при потолке 14 |
| Есть прибыльные параметры | Нет — 0 из 144 |

Ключевое — вторая и третья строки. При нулевых издержках стратегия даёт
+0.033R на сделку, а случайные входы с той же геометрией — **+0.071R**, вдвое
больше. То есть плюс до издержек создан не выбором момента, а ATR-стопом,
целью 1:2 и дрейфом рынка. Индикаторы не бесполезны — они выбирают моменты
**хуже монетки**, и делают это последовательно в обоих замерах.

Добивает арифметика: пошлина на этом таймфрейме −0.15R на сделку (см. раздел
про пошлину ниже), а вся геометрия даёт +0.07R. Конструкция была обречена
раньше, чем кто-либо посмотрел на индикаторы.

Поэтому на вкладке «Сигналы» над карточками висит предупреждение. Карточки не
убраны — движок работает и должен показывать то, что выдаёт, — но смотреть на
них, не зная измеренного результата, нельзя.

**Это не финансовая рекомендация.** Инструмент технического анализа.

## Что уже работает

**Живые данные биржи**
- По умолчанию источник — **Binance** (публичные endpoint'ы, без ключей и ордеров).
- Цены опрашиваются каждые ~10 секунд одним пакетным запросом на все монеты.
- Открытые сигналы закрываются **по текущей цене**, а не по закрытию свечи —
  так же, как бэктест считает, что стоп внутри свечи исполнился.
- Если биржа недоступна, сервер прямо об этом пишет и не притворяется рабочим.

**Сигналы**
- Конфлюэнс-движок: тренд (EMA 21/50/200), импульс (MACD), сила тренда (ADX/DMI),
  перегрев (RSI), объём, подтверждение старшим таймфреймом.
- Фильтр флэта: при ADX ниже порога сигналов нет вообще.
- Стоп по волатильности (ATR), тейк по заданному соотношению риск/прибыль.
- В карточке явно указано, **на каком уровне фиксировать прибыль и убыток** —
  цена, процент движения и результат в R.
- **Вероятность успеха** с доверительным интервалом и размером выборки.
- У каждого сигнала — score 0–100 и список причин человеческим языком.

**Проверка**
- Бэктест по всем монетам: винрейт, средний R, profit factor, сумма R, просадка.
- Живой трек-рекорд опубликованных сигналов.
- Комиссия и проскальзывание вычитаются с обеих сторон сделки.
- **Проверка на устойчивость** (`npm run validate`) — две отдельные проверки,
  и обе могут провалиться:
  - *во времени*: сделки разбиваются на отрезки. Если весь результат сделан
    одним удачным периодом, это видно, а не усредняется;
  - *к параметрам*: та же логика прогоняется по сетке из 96 наборов порогов.
    Прибыль только при одной точной настройке — признак подгонки; широкое
    плато прибыльных настроек — признак, которому можно доверять.

**Надёжность данных**
- Каждая серия свечей проверяется на пропуски, дубли, нарушения порядка,
  битые значения и устаревание ленты. На подозрительных данных новый сигнал
  **не выдаётся** — испорченная свеча сдвигает все индикаторы, и результат
  выглядит совершенно нормально.
- Открытые позиции при этом всё равно доводятся до конца: бросать их из-за
  сбоя ленты нельзя.
- Запросы к бирже — с ретраями, экспоненциальной паузой и переключением на
  зеркала. Молчаливая остановка ценового цикла хуже ошибки: сигналы перестают
  закрываться, и трек-рекорд незаметно замерзает.

**История**
- Все закрытые сигналы помечены: <b>✓ Успешный</b>, <b>✗ Неудачный</b> или <b>○ Истёк</b>.
- Рядом с каждым — заявленная в момент выдачи вероятность, чтобы можно было
  сверить обещание с фактом.
- Сводка калибровки: средняя заявленная вероятность против фактического результата.

**Сайт**
- Карточки активных сигналов с живой ценой, прогрессом между стопом и тейком
  и текущим P&L в единицах риска.
- Обзор рынка: состояние индикаторов по каждой монете.
- История всех закрытых сделок, включая убыточные и истёкшие.
- Статистика: живой результат рядом с бэктестом + описание методики.
- График со свечами и отмеченными уровнями входа/стопа/тейка.
- Живое обновление через SSE.

## Сайт работает сам, без сервера

Дашборд опубликован через **GitHub Pages** и не требует ни хостинга, ни
запущенного процесса:

- **GitHub Actions по расписанию** (заявлено ежечасно) забирает данные с
  Binance, прогоняет ту же логику, закрывает дошедшие до стопа/тейка сигналы и
  коммитит результат в `data/*.json`.
- **Pages отдаёт статическую страницу**, которая читает эти JSON.
- **Цены в карточках** страница берёт с Binance напрямую из браузера, поэтому
  они двигаются в реальном времени, а не раз в час. Если браузер не может
  достучаться до биржи, показывается снимок с последнего скана — и об этом
  прямо написано рядом.

### Честно про расписание: cron на GitHub здесь не работает

Измерено на этом репозитории за первые 12.7 часов жизни workflow. Всё это время
workflow был в состоянии `active` — то есть дело не в отключении по неактивности:

| Расписание | Слотов | Сработало |
|---|---:|---:|
| `*/15` (каждые 15 минут) | ~33 | **1** |
| `5,35` (дважды в час) | 2 | **0** |
| `4 * * * *` (ежечасно) | 2 | **0** |

**Один запуск там, где запрошено ~37.** Все остальные прогоны — от пушей.

Промежуточная версия этого раздела утверждала, что часовые слоты GitHub
отрабатывает охотнее: единственный сработавший прогон пришёлся ровно на 10:00.
Через два часовых слота гипотеза не подтвердилась — это было совпадение.
Оставляю запись об ошибке, а не переписываю задним числом.

Ежечасно — по-прежнему правильная **просьба**: новые сигналы решаются на
закрытых часовых свечах, между ними искать нечего, а чем реже просишь, тем
меньше шансов, что GitHub отбросит. Но полагаться на это нельзя, поэтому
**сайт не обещает частоту — он показывает измеренный возраст данных**. Старше
150 минут (два пропущенных часа) — вместо обычной плашки предупреждение.
Обновить вручную всегда можно: Actions → «Скан рынка» → Run workflow.

Пропущенный час стоит упущенных сигналов, но не ошибок: скан всегда читает
свежайшую закрытую свечу, а открытые позиции закрываются по истории свечей —
записанный результат сделки одинаков, заметили её вовремя или через пять часов.
Поэтому это оставлено как есть, а не обойдено костылём.

Если понадобится настоящая ежечасная надёжность, вариантов ровно три:
смириться; внешний бесплатный cron, дёргающий `repository_dispatch` (нужен
токен, который создаёте вы); или крошечный постоянно работающий хост — Node-
сервер в этом репозитории для этого уже готов. Гонять Actions непрерывным
job'ом сознательно не стал: это использование раннеров как бесплатного
сервера, и рисковать за это аккаунтом не стоит.

Побочный эффект, который дороже, чем кажется: история сигналов лежит в
git-коммитах. Её нельзя переписать задним числом незаметно.

Тот же код работает и за Node-сервером (`npm start`) — режим определяется
автоматически, настраивать ничего не нужно. Под сервером появляются живой
поток SSE и кнопки ручного запуска.

### Что нужно включить один раз

В **Settings → Pages** источником должен быть `main` / корень репозитория.
После этого сайт доступен по адресу вида `https://<логин>.github.io/<репозиторий>/`.

Первый скан можно не ждать: **Actions → «Скан рынка» → Run workflow**.

## Другие проверки из GitHub

Если под рукой только телефон, локально ставить ничего не нужно — проверки
живут в GitHub Actions, а результат читается прямо в приложении GitHub.

**Проверка на живых данных биржи.** Вкладка **Actions** → workflow
*«Проверка на живых данных биржи»* → **Run workflow**. Можно выбрать источник,
таймфрейм и список монет. Через несколько минут в **Summary** появится отчёт:
связь с биржей и какой хост ответил, качество данных по каждой монете, бэктест
и обе проверки на устойчивость. Тот же отчёт сохраняется файлом `report.md` во
вкладке артефактов.

Запускается ещё и по расписанию, раз в неделю — чтобы видеть, держится ли
результат со временем.

**Глубокий анализ.** Вкладка **Actions** → workflow *«Глубокий анализ»* →
**Run workflow**. Можно задать глубину истории (по умолчанию 8000 часовых
свечей на монету — около года) и долю выборки для подбора настроек. Работает
несколько минут: качает историю постранично, прогоняет стратегию и считает
детальную статистику. Результат появляется на вкладке **«Аналитика»** на сайте
и в **Summary** прогона. Раз в неделю запускается сам.

**Сбор фандинга.** Вкладка **Actions** → workflow *«Сбор фандинга»* →
**Run workflow**. Измеряет не стратегию, а сколько платят за удержание
непопулярной стороны бессрочного фьючерса: ставки финансирования по 25
перпетуалам, минимальный срок удержания, проверка отбора вне выборки против
случайного выбора, риск ликвидации шорт-ноги. Результат — на вкладке
**«Фандинг»** и в **Summary**. Раз в неделю запускается сам.

**Тесты** гоняются сами на каждый пуш и в каждом PR, там же во вкладке Actions.

Это и есть способ проверить адаптер Binance на реальном соединении: раннеры
GitHub видят биржу, среда разработки — нет.

## Запуск локально

```bash
npm install
npm start
```

Откройте <http://localhost:3000>.

Работает сразу на живых данных Binance — ключи API не нужны, ордера не
выставляются, используются только публичные endpoint'ы.

Если `api.binance.com` заблокирован в вашем регионе или сети:

```bash
BINANCE_BASE_URL=https://data-api.binance.vision npm start
```

Демо без сети (синтетические данные, сайт предупреждает об этом баннером):

```bash
COINSCOPE_SOURCE=synthetic npm start
```

Бэктест из командной строки:

```bash
npm run backtest
```

Проверка стратегии на устойчивость (занимает пару минут — прогоняется вся сетка):

```bash
npm run validate
```

**Наполнить историю сразу.** Свежий сигнал идёт к стопу или тейку часами, поэтому
на новой установке история пуста. Реплей прогоняет прошлые свечи через ту же
логику выдачи и закрытия:

```bash
npm run replay
```

Такие сигналы помечены как «реплей», в **живой** трек-рекорд не попадают
(их никто не публиковал в реальном времени), но учитываются как доказательная
база для оценки вероятностей — наравне со сделками бэктеста.

## Как считается результат

- **R** — результат в единицах риска. +1R = заработали столько, сколько рисковали.
- Вход по закрытию сигнальной свечи; исход определяется только по следующим свечам.
- Если свеча задела и стоп, и тейк — засчитывается **стоп**. Порядок движения
  внутри свечи неизвестен, и предполагать выгодный — значит врать себе.
- Сигнал, не дошедший ни до одного уровня за `expiryBars`, закрывается по рынку
  и всё равно попадает в статистику.
- Одна открытая позиция на монету.

### Откуда берётся вероятность успеха

Это **не прогноз модели**, а измеренная доля успешных среди похожих завершённых
сигналов: тот же таймфрейм и диапазон score, по возможности та же монета и
направление. В доказательную базу входят сделки бэктеста и уже закрытые сигналы.

Если похожих сигналов меньше `COINSCOPE_MIN_PROB_SAMPLE`, сравнение расширяется
по шагам (та же монета → то же направление → любой score), и каждый шаг явно
подписан в карточке. Если даже так данных не хватает — вместо числа написано
«нет оценки». Рядом всегда стоит доверительный интервал Уилсона и размер
выборки, а оценка **замораживается на момент выдачи**, чтобы историю нельзя
было задним числом переписать.

### Детальная статистика и почему она устроена так

Вкладка **«Аналитика»** — это диагностика, а не витрина. Сделки режутся по
score, направлению, монете, силе тренда, RSI, объёму, волатильности,
удалённости от EMA200, торговой сессии и дню недели. Задача каждой нарезки —
показать, где логика не работает, а не найти красивую цифру.

Такая нарезка опасна, и вот чем: если разделить любые данные на сорок групп и
проверять каждую на уровне 5%, две группы будут выглядеть «значимыми» просто
по построению. Поэтому:

- **Никаких голых процентов.** Каждая группа показана с доверительным
  интервалом — винрейт по Уилсону, средний R по стандартной ошибке. Интервал и
  есть честная ширина числа.
- **Считается цена случайности.** Рядом с каждой нарезкой написано, сколько
  групп проверено и сколько «значимых» дала бы чистая случайность. Находкой
  считается только превышение над этим числом.
- **Есть контрольная нарезка.** День недели включён намеренно: осмысленной
  связи там быть не должно. Если «связь» находится и там — это калибровка того,
  насколько врёт случайность на этой выборке.
- **Малые группы не считаются доказательством.** Меньше 25 сделок — строка
  показывается бледной и никогда не помечается значимой.
- **Подбор настроек проверяется на невиданных данных.** Лучший набор
  параметров выбирается на первых 70% истории и оценивается на последних 30%,
  которых подбор не видел. Разрыв между двумя числами — это измеренный размер
  подгонки. Подобранный набор **не применяется автоматически**: выбрать
  максимум и объявить его настройкой — ровно то, от чего эта проверка защищает.

### Шире вселенная — чаще сигналы (и только это)

Сигнал требует редкого совпадения условий, поэтому частота его появления
масштабируется числом наблюдаемых монет, а не мягкостью порогов. Ослабить
пороги — тоже способ получить больше сигналов, но это покупка частоты снижением
планки, то есть ровно противоположное тому, что нужно. Поэтому монеты
выбираются автоматически по обороту за сутки (`COINSCOPE_UNIVERSE`).

Порог оборота (`COINSCOPE_MIN_VOLUME`, по умолчанию $50M) — это **не фильтр
качества, а фильтр честности**. Модель издержек берёт фиксированные 0.05%
проскальзывания; на паре с оборотом в сотни миллионов это защитимо, на тонкой —
выдумка. Пустить тонкие монеты по издержкам ликвидных значит бесплатно завысить
любой результат. Заодно отсекаются стейблкоин-пары (у них нечему двигаться) и
плечевые токены (они следят за деривативом, а не за монетой).

**Имён недостаточно — нужен механизм.** Первый прогон на расширенной вселенной
поймал RLUSD (доллар от Ripple): он прошёл и порог оборота, и список
стейблкоинов, которого не знал его тикер, и дал **−8.7R на сделку**. Монета,
привязанная к доллару, почти не двигается, поэтому ATR-стоп у неё — доли
процента, а фиксированные 0.2% круговых издержек становятся многократным риском.
Одна монета из пятнадцати сдвинула портфель с −0.12R до −0.41R и дала −1233R из
−1514R.

Вывод не «дописать RLUSD в список», а сделать фильтр самим механизмом: любая
монета, у которой пошлина превышает `COINSCOPE_MAX_TOLL` (по умолчанию 0.5R),
исключается — её не спасёт никакая стратегия. Это ловит все нынешние и будущие
стейблкоины, привязанные активы и всё слишком тихое, чтобы окупить исполнение.
Исключения печатаются с числами, а не происходят молча.

Что расширение вселенной **не** делает: оно не создаёт преимущества. Оно даёт
больше данных о той стратегии, какая есть. Если она проигрывает случайным
входам на восьми монетах, на сорока она будет проигрывать им точнее.

### «Пусть система учится после каждого сигнала»

Самая естественная просьба и самая вредная в этой задаче — и дело в отношении
чисел, а не во вкусах.

Разброс результата одной сделки — около 1R. Край, который вообще ищут, —
порядка 0.05R. Значит, в одной сделке примерно одна двадцатая сигнала,
закопанная в целую единицу шума, и чтобы отличить край 0.05R от нуля, нужно

    n = (2 / край)²  ≈  1600 сделок

Правило, которое подстраивается после каждого исхода, реагирует на одну
тысячную той выборки, по которой можно понять, было ли чему учиться. Оно гонится
за тем, что только что произошло, а произошла в основном удача.

Это теория, поэтому она проверяется. **Walk-forward** — честная версия
обучения: история режется на последовательные окна, для каждого окна настройки
подбираются только по предыдущим, окно торгуется ими, результат записывается.
Каждый результат вне выборки по построению, а процедура повторяет то, что
делает адаптивная система — переобучение на прошлом, действие в будущем, — но с
честной частотой: тысячи сделок на обновление, а не одна.

Сравнение идёт с настройками, которые не меняются вообще. Если адаптация чего-то
стоит, она их обыгрывает. Если нет — «обучение» это более дорогой способ следить
за шумом, и измерение об этом скажет. Отдельно показывается **недобор**: на
сколько выбранный набор обещал больше, чем потом дал. Это цена подгонки,
измеренная на каждом шаге.

Что при этом накапливается честно и действительно улучшается с опытом:
оценка вероятности у сигнала. Она не модель, а подсчёт исходов среди похожих
завершённых сделок, и чем их больше, тем она точнее. Расширение вселенной
помогает именно ей.

### Плечо — следствие, а не выбор

«С каким плечом входить» звучит как свойство сигнала. Это не так: его полностью
определяют два числа — сколько счёта вы готовы потерять на стопе и как далеко
стоп стоит.

    позиция / счёт  =  риск %  /  расстояние до стопа %

Риск 1% при стопе в 1.5% — позиция 0.67 счёта, плечо не нужно вовсе. Плечо
больше 1 появляется только тогда, когда стоп **ближе** принятого риска, и это
опасное направление: чем ближе стоп, тем крупнее позиция.

Карточка сигнала показывает размер позиции, плечо (или «без плеча»), расстояние
до ликвидации и предупреждение, если размер опасен. Опасность считается по трём
независимым механизмам, потому что одного мало:

1. **ликвидация близко к стопу** — фитиль достаёт её раньше, чем исполнится
   стоп, и стоп перестаёт быть стопом;
2. **стоп не окупает исполнение** — та же арифметика пошлины: стоп в 0.1% при
   круговых 0.2% это 2R издержек на сделку;
3. **гэп на высоком плече** — стоп не защищает от разрыва цены, и при 10×+
   обычный гэп уносит счёт целиком.

Позиция 50× за стопом в 0.1% проходит первую проверку с запасом в 15× и
проваливает две остальные. Поэтому критерий один — не годится.

**Главное про плечо: оно не меняет результат в R.** R уже нормирован на риск,
поэтому вдвое большее плечо удваивает и прибыли, и убытки, а средний R остаётся
тем же. Плечо не превращает убыточную стратегию в прибыльную — оно решает только,
насколько быстро закончится счёт. Критерий Келли на текущих данных даёт
**отрицательную** долю, и у этого точный смысл: не существует положительного
размера позиции, который наращивает счёт.

### Серия убытков: невезение или сломанный учёт

Полоса проигрышей всегда вызывает один вопрос — «а не сломалось ли что-то?», — и
честный ответ на него число, а не утешение. Сравнение живого результата с
винрейтом из бэктеста считается автоматически.

Шесть убытков подряд при винрейте 36% случаются в **7%** случаев: не повезло,
совершенно обычное дело, признаков бага нет. Шесть убытков из двадцати — событие
с вероятностью 0.01%, и это уже означает, что живое исполнение разошлось с
историческим расчётом, то есть **ошибку в коде**, а не стратегию похуже.

Проверка нужна потому, что снаружи эти два случая выглядят одинаково, а делать
надо противоположные вещи.

### Нулевые модели: как выглядит «умения нет» на этих же данных

Доверительные интервалы и «5% ложных срабатываний» опираются на допущение,
что сделки независимы. Здесь это неправда: соседние сделки идут в одном
рыночном режиме, поэтому эффективная выборка меньше, чем число сделок, а все
аналитические интервалы уже, чем должны быть. Вместо того чтобы допущение
чинить, уровень шума **измеряется**: те же данные прогоняются через тот же
конвейер так, чтобы связи в них не было по построению.

**Случайные входы.** Те же монеты, то же соотношение лонг/шорт, та же
геометрия стопа и цели, те же правила выхода — случаен только момент входа.
Это изолирует единственное, что делают индикаторы. Если стратегия не
обыгрывает монетку, логика входа не добавляет ничего, и настраивать пороги
бессмысленно. Проверка стоит первой на вкладке именно поэтому.

**Поворот результатов.** Таблицы разрезов пересчитываются с результатами,
сдвинутыми по кругу на чужие сделки. Именно поворот, а не перемешивание:
он сохраняет «полосатость» серии результатов и разрушает только её привязку
к признакам — то есть ровно то, что проверяется. Сколько «значимых» групп
конвейер находит на таких данных, столько и стоит его разметка. На синтетике
измеренный потолок оказался втрое выше арифметического.

**Издержки.** Уровни стопа и цели от комиссии не двигаются, поэтому сделки
просто пересчитываются под другие издержки. Главное число — результат при
нулевых: если и там минус, дело не в исполнении и дешёвая биржа не поможет.

### Пошлина: арифметика, которая решает всё до всяких индикаторов

Издержки берутся долей от **цены**, а результат меряется долей от **стопа**.
Значит:

    пошлина в R  =  круговые издержки, %  /  ширина стопа, %

Это отношение задано таймфреймом и множителем стопа — не сигналом. На часовых
свечах стоп в 1.5×ATR это порядка 1–2% от цены, круговые издержки около 0.2%,
и каждая сделка стартует примерно с **−0.13R**. Преимущество должно превышать
это число, чтобы просто выйти в ноль, — а 0.13R на сделку это очень много по
меркам любого опубликованного края.

Практический вывод: **пороги эту арифметику не двигают вообще, а таймфрейм
двигает в разы.** Поэтому число считается и показывается до всякой стратегии —
оно дисквалифицирует конструкцию раньше, чем на сигнальную логику потрачено
время. Отдельно проверяется, различает ли источник таймфреймы вообще: у
синтетического генератора ATR одинаков в долях цены на всех масштабах, поэтому
на нём сравнение бессмысленно, и отчёт об этом прямо пишет вместо того, чтобы
объявлять победителя по разнице в округлении.

### Сейф: последняя часть истории, которую подбор не видит никогда

Проверка на отложенной выборке честна ровно **один раз**. Дальше вы читаете
её результат, он влияет на следующую идею, вы перезапускаете — и через
несколько итераций «невиданные» данные становятся обучающими через вас.
Код этого не замечает: отчёт всё так же пишет «на невиданных данных» и всё
так же выглядит строго.

Поэтому последние 20% истории убираются до всех расчётов и не участвуют ни в
одном числе отчёта. Открыть их — отдельное действие
(`COINSCOPE_OPEN_VAULT=1`), и каждое открытие дописывается в `data/vault.json`,
который лежит в git. Значение имеет **число открытий**: открытый один раз сейф
— честная проверка, открытый десять раз — обучающая выборка окольным путём.
Журнал существует, чтобы это нельзя было забыть.

Отдельно считается **калибровка**: из сигналов, которым сайт написал «60%»,
выиграли ли примерно 60%. Это проверка честности самого числа рядом с сигналом,
и считается она по реально выданным сигналам, а не по бэктесту.

И **ход цены** (MFE/MAE): убыточная сделка не пошла никуда или дошла почти до
цели и развернулась? Это разные проблемы. Одна лечится входом, другая выходом,
а винрейт не различает их вовсе. У этой метрики есть честное ограничение: у
выигрышных сделок она обрезана целью — сделка там заканчивается, и куда цена
пошла бы дальше, из этих данных не узнать. Поэтому информативны числа по
убыточным, а вопрос «а если цель подвинуть» решается перезапуском стратегии с
другой целью, а не экстраполяцией.

### Сбор фандинга: другая сделка, где платят не за угадывание

Всё выше — про сигналы, то есть про попытку угадать направление. Измеренный
край там отрицательный, и никакая настройка порогов этого не меняет: мешает
арифметика, а не точность. Поэтому в проекте появилась вторая, принципиально
другая вещь, и у неё своя вкладка — **«Фандинг»**.

У бессрочного фьючерса нет экспирации, значит ничто не держит его у цены спота.
Биржа держит его выплатой: каждые несколько часов сторона, которой больше,
платит той, которой меньше. Ставка публикуется заранее и одинакова для всех.
Купить монету на споте и зашортить столько же бессрочного — движения цены
взаимно гасятся, остаётся выплата. **Здесь ничего не угадывают:** деньги платят
за то, что вы держите непопулярную сторону, а не за то, что вы оказались правы.

Это не означает «бесплатные деньги», и модуль существует ровно затем, чтобы
посчитать четыре вещи, которые их забирают:

1. **Пошлина, снова.** Две ноги, четыре пересечения спреда: вход в спот, вход
   в шорт, выход из обоих. Это около 0.40% от номинала против типичной выплаты
   0.01% раз в 8 часов — то есть порядка сорока выплат, около двух недель,
   только чтобы отбить собственное исполнение. Поэтому «собирать фандинг»
   на пару дней означает оплачивать свои комиссии.
2. **Отрицательный фандинг.** Когда перпетуал уходит ниже спота, платим мы.
   Зеркальная сделка (лонг перп + шорт спота) **не симметрична**: шорт спота
   требует занимать монету по ставке, которую никто не публикует заранее.
   Поэтому минусовые периоды — это издержка, а не возможность.
3. **Капитал, а не номинал.** Спот оплачивается целиком. При плече 3× на шорте
   один доллар капитала держит 0.75 доллара номинала — и привычное «фандинг ×
   число выплат в году» завышает доходность ровно на эту величину. Это самая
   частая ошибка в таких расчётах, и в отчёте оба числа стоят рядом.
4. **Базис и ликвидация.** Ноги гасят движение цены только пока обе открыты:
   войти на широком базисе и закрыться на узком — реальный убыток, сколько бы
   ни заплатил фандинг. А резкий рост ликвидирует шорт раньше, чем спот успеет
   помочь: прибыль спота лежит в другом аккаунте и ликвидацию не останавливает.

Проверяется это той же машинерией, что и стратегия, и по тем же правилам:
ранжирование монет считается на первой половине истории, а проверяется на
второй, которую ранжирование не видело; рядом обязательно стоит **случайный
выбор такого же размера** (когда почти все монеты платят положительный фандинг,
любой набор выглядит прибыльным вне выборки — без этого сравнения «топ-5
заработал больше вселенной» не значит ничего); последние 20% истории
откладываются и не участвуют ни в одном числе.

Интервал выплат **не предполагается**, а измеряется по самим отметкам времени:
большинство перпетуалов платят раз в 8 часов, часть — раз в 4, и расписание
меняют. Иначе четырёхчасовая монета была бы молча показана вдвое беднее, чем
есть. Берётся медиана промежутков, а не среднее: одна смена расписания оставляет
гигантский разрыв, и среднее увело бы годовой множитель для всей выборки.

Есть и отдельная защита от самого лестного из возможных артефактов. Если базис
выходит ровно нулевым, это не идеальная нейтральность — это один и тот же ряд,
поданный как обе ноги (так делает генератор для тестов, у него нет отдельного
перпетуала). Отчёт в таком случае говорит «не измерен» вместо «0.00%», потому
что ноль здесь выглядит как отсутствие единственного нехеджированного риска
сделки. По той же причине запуск на генераторе вообще не выносит рыночного
вердикта: генератор строит каждую монету вокруг фиксированной средней ставки,
так что отбор на нём «работает» по построению.

Запуск: **Actions** → *«Сбор фандинга»* → **Run workflow** (раз в неделю идёт
сам). Результат — на вкладке **«Фандинг»** и в **Summary** прогона.

#### Важное ограничение: из GitHub Actions фандинг пока не измерен

Три живых прогона выяснили — по одному хосту за раз — что деривативные API
закрыты для раннеров GitHub, тогда как спот Binance с той же машины отвечает
прекрасно:

| Хост | Ответ |
|---|---|
| `fapi.binance.com` | `451` — «Service unavailable from a restricted location» |
| `fapi1`, `fapi2` | `202` с пустым телом — тот же шлагбаум другой формы |
| `api.bybit.com` | `403` — «CloudFront … block access from your country» |
| `api.binance.com` (спот) | работает |

Каждое такое открытие стоило мерджа, прогона и отчёта. Поэтому появился
**зонд доступности** (*Actions → «Зонд доступности»*): он спрашивает все
кандидаты сразу — Binance futures, публичный архив `data.binance.vision`,
bybit, OKX, gate.io, bitget, deribit, hyperliquid — и печатает таблицу с
ответами. Дальше адаптер пишется под хост, который **уже ответил**, а не под
предполагаемый.

Зонд сознательно глупый: без повторов, без failover, без разбора тела кроме
обрезка. Его ценность в том, что он сообщает, а не толкует. Первая версия этого
всё-таки не удержала и объявила любой 403 «гео-блоком CloudFront по стране» —
а в песочнице разработки каждый 403 оказался egress-политикой самой среды.
Зонд уверенно назвал неверную причину, внутри инструмента, созданного ровно
против этого. Теперь причина читается из тела ответа, а когда тело молчит —
печатается статус без выдуманного объяснения. И если закрыт даже контрольный
хост, зонд первым делом говорит, что таблица описывает эту машину, а не биржи.

#### Что зонд показал на самом деле

Картина оказалась шире, чем я утверждал раньше. Я говорил, что «спот Binance с
тех же раннеров работает прекрасно» — **это неверно**:

| | Хост | Ответ |
|---|---|---|
| ❌ | `api.binance.com` (спот) | `451` — restricted location |
| ✅ | `data-api.binance.vision` | отвечает — на нём и держится весь проект |
| ❌ | `fapi.binance.com` | `451` — restricted location |
| ✅ | архив `data.binance.vision` | отвечает |
| ❌ | `api.bybit.com` | `403` — CloudFront по стране |
| ✅ | `okx`, `gate.io`, `bitget`, `deribit`, `hyperliquid` | отвечают |

Спотовый хост Binance закрыт тоже. Проект работает лишь потому, что в списке
хостов вторым стоит `data-api.binance.vision` — это failover, а не доступность.
Зато шлагбаум оказался специфичным для Binance и Bybit: пять других площадок
отвечают.

По этому измерению и выбрана **OKX** — единственная из открытых, у которой есть
и спот, и бессрочные контракты по одной монете. Значит, базис считается **внутри
одной площадки**, а не как спред между двумя биржами: это более узкий и более
честный риск. Если спот-нога всё-таки берётся с другой биржи, отчёт отдельно
говорит, что базис стал межбиржевым — одно и то же число означает разное.

Три вещи в OKX отличаются от Binance, и каждая ломается молча, поэтому у каждой
свой тест: символы вида `BTC-USDT-SWAP`, строковый `code` в конверте ответа, и
оборот, который надо **вычислять**, а не читать (`volCcy24h` — в базовой валюте,
так что для каждой монеты это разная величина; ранжировать по нему напрямую
значило бы поставить дешёвую монету с огромным числом единиц выше ликвидной).

#### Первый живой прогон упал, и обе причины стоит запомнить

Он прожил 16 секунд и выдал `SyntaxError: Unexpected end of JSON input` из
внутренностей undici. Причина: `/fapi/v1/ticker/24hr` ответил **200 с пустым
телом**, а код на `res.ok` сразу вызывал `res.json()`. Успешный статус — это
утверждение о транспорте, а не о содержимом. Теперь тело читается как текст и
разбирается явно: пустое или не-JSON тело при 200 считается плохим ответом,
повторяется, а потом уходит на зеркало — и в сообщении видно хост, путь и что
именно пришло. Заодно вселенная получила второй маршрут: если фьючерсный тикер
молчит, список перпетуалов берётся из каталога контрактов (`exchangeInfo`, там
же видно `contractType`, так что квартальные поставочные контракты не попадут
в выборку), а ранжирование — по обороту спота с `api.binance.com`.

**Второй живой прогон упал иначе, и это оказалось важнее.** Починенный код
наконец сказал правду:

```
Binance futures 202 on /fapi/v1/exchangeInfo (https://fapi2.binance.com):
пустое тело ответа
```

**Статус 202 с пустым телом, со всех трёх фьючерсных хостов.** Так не отвечает
API — так отвечает заградительный слой. Спотовый `api.binance.com` с тех же
раннеров работает прекрасно: этот проект качает с него тысячи свечей каждый час.
Значит, «брать фандинг с Binance» — ненадёжный план из дата-центра.

Вывод не «починить Binance», а что измерение не должно зависеть от одной
площадки. Вопрос ведь не про Binance: измеряется, сколько **рынок** платит за
удержание непопулярной стороны перпетуала. Поэтому площадки пробуются по
очереди — Binance futures, затем bybit (публичная история фандинга, те же имена
символов, оборот сразу в котируемой валюте), — и отчёт говорит, кто ответил.
Если ноги оказываются на разных площадках (шорт на bybit, спот на Binance), это
рабочая конструкция, но базис там — спред **между** биржами, шире
внутриплощадочного, и отчёт это отдельно проговаривает.

Заодно выяснилось, что мой же обходной маршрут был сломан ровно той же
ошибкой: он начинался с `/fapi/v1/exchangeInfo`, то есть падал там же, где
основной путь. Обход, которому нужно, чтобы шлагбаум открылся, — не обход.
Последний маршрут теперь не трогает фьючерсные хосты вовсе: ранжирование по
обороту спота, а есть ли у символа перпетуал, решает сам запрос истории —
монета без истории просто выпадает.

И каждый HTTP-запрос теперь пишется в журнал со статусом и размером тела, а при
полном отказе журнал печатается целиком. Две неудачных попытки ушли на то, чтобы
узнать то, что обычный стек отказывался сказать: какой хост, какой путь, какой
статус и пришло ли тело вообще.

Третье: та же ошибка `res.ok` → `res.json()` нашлась и в спотовом адаптере.
Там она ни разу не выстрелила, но механизм был тот же, и следующий шлагбаум мог
прийти туда. Исправлено и там.

Второе оказалось хуже первого. Шаг был написан как
`node server/cli-funding.js | tee funding.log`, а код возврата конвейера — это
код `tee`. Поэтому упавшее измерение отчиталось как **успешное**, и сбой
всплыл двумя шагами позже как `pathspec 'data/funding.json' did not match any
files` — сообщение, которое указывает на git вместо настоящей ошибки. Оба
длинных воркфлоу пишут через `tee`, так что `shell: bash` (а с ним
`-o pipefail`) добавлен в оба, и в наборе тестов есть проверка, которая этого
требует.

## Архитектура

```
server/
  config.js       параметры и пороги (всё переопределяется env)
  indicators.js   EMA, RSI, MACD, ATR, ADX/DMI, Bollinger — чистые функции
  strategy.js     конфлюэнс-движок: score, направление, уровни
  backtest.js     прогон по истории + учёт комиссий + статистика
  tracker.js      живой цикл: сканирование и доведение сигналов до конца
  probability.js  оценка вероятности по фактическим исходам + интервал Уилсона
  dataQuality.js  аудит свечей: пропуски, дубли, порядок, устаревание
  validate.js     устойчивость во времени и к параметрам (анти-подгонка)
  replay.js       прогон прошлых свечей через ту же логику (наполнение истории)
  staticRun.js    прогон без сервера и без БД: пишет data/*.json для Pages
  db.js           SQLite: сигналы, исходы, бэктесты (только для локального сервера)
  sources/        binance.js (боевой) и synthetic.js (офлайн) за одним интерфейсом
index.html        дашборд (Pages отдаёт его из корня)
assets/           стили и клиент — один код для статики и для сервера
data/             JSON, который коммитит плановый скан; его читает сайт
```

## Ограничения

- Стратегия одна — трендследящая. На затяжном флэте она молчит, и это
  сознательно: лучше не дать сигнал, чем дать плохой.
- **Измеренное преимущество отрицательное** (см. раздел выше). Пока это так,
  сигналы — материал для проверки гипотез, а не для торговли.
- **Окно истории короткое.** ~500 часовых свечей это около 20 дней, то есть
  один режим рынка. На таком отрезке нельзя ни подтвердить стратегию, ни
  окончательно её похоронить. Следующий честный шаг — постраничная загрузка
  klines за куда более длинный период и повторный прогон проверок.
- Адаптер Binance работает в GitHub Actions (реальный скан прошёл: 8 монет,
  500 свечей, 0 пропусков). В среде разработки биржевые API закрыты политикой
  сети, поэтому там используется синтетический источник.
  Он нужен только для разработки и тестов и ничего не говорит о реальном рынке.
- Нет исполнения ордеров. Только сигналы.
- **Сбор фандинга измеряется, но не исполняется.** Отчёт говорит, сколько рынок
  платил за удержание нейтральной позиции и чего это стоило бы; заводить две
  ноги, следить за маржой шорта и пополнять её — не делает ничего. И ставка
  прошлого не обещает ставку будущего: фандинг высок, когда в лонгах тесно,
  и сжимается, когда туда приходят за этой же выплатой.
